# 鲸鲸约跑

替你跑完这两公里 · 你只管去刷脸。

**不申请定位权限，不连服务器，不需要登录。**

适用于 HarmonyOS 4.0（Android 12 基底）及所有 Android 7.0+ 设备。

---

## 界面结构

**两个页面，各只干一件事**（G1.11.1 起）。不引 Fragment / 导航库，
页面之间走标准 Activity 转场，侧滑返回由系统提供（守住「零第三方依赖」）。

```
主页 MainActivity                    设置 SettingsActivity
├── 顶栏（标题 + 日志 + 设置）        ├── 账号：openid / 连接 / 场地
├── 地图（边界 / 禁跑区 / 轨迹）      ├── 跑步：配速 / 距离 / 抖动 / 拟真轨迹
├── 倒计时（3 秒，盖在地图上）        ├── 统计：记录卡片 → 全屏轨迹 + 导出 GPX
├── 状态卡（环 + 剩余 / 已跑 / 配速）  ├── 教程：使用步骤 + 复制 / 分享脚本
└── 底部固定【开始打卡】              ├── 流体云：胶囊状态 + 测试胶囊
   跑步中变成【暂停】【结束打卡】
                                      ├── 外观：主题
运行日志是独立一页 LogActivity        └── 关于：版本 / 本项目仓库 / 原仓库
```

主页**不塞表单**：场地 / 配速 / 距离 / 抖动都属于「设置」。

### 开跑前的 3 秒倒计时

点【开始打卡】后，地图上立刻盖一层倒计时（`CountdownView`）：压暗的地图 + 一个环 +
大号秒数 + 一行「再点一次可取消」。**倒计时结束前再点一次按钮就取消。**

它解决的是一个具体的体验问题：点下去之后引擎要先换 token、拉场地、生成轨迹，
几百毫秒到一两秒不等，这段时间界面毫无反馈，人会以为没点上，于是再点一下 ——
那一下就可能是重复触发。

实现上有两个关键点：

- **倒计时和数据准备并行**：3 秒足够把 token 换完、轨迹算好，于是倒计时一结束就
  立刻开跑，不会出现「倒计时走完还要再等两秒」。弱网下倒计时先走完，就把状态改成
  「准备中」继续等，数据到了再启动 —— 不为了凑这 3 秒去砍掉准备步骤。
- **`runSeq` 作废旧结果**：取消时把序号 +1，在途的准备线程 post 回来发现序号对不上
  就直接丢弃，不会把「上一轮的准备」跑到下一轮头上。

倒计时期间按钮固定是【取消】（`refreshRunButton()` 提前 return），
状态广播也不会盖掉仪表盘；离开页面（`onStop`）视为放弃，直接取消。

> openid 填在设置页。填完回主页时会**自动刷新场地列表**（`AreaStore` +
> `onResume` 里的自动补拉），不需要先点一次【开始打卡】。

主题切换在【设置】页，是「跟随系统 / 深色 / 浅色」三段式，不是一个循环按钮。

## 流体云（G1.11.1 起）

打卡进度是一条**实时活动通知**：状态栏上收成胶囊，展开是带进度条的卡片。
在 ColorOS 16 上它就是**流体云**。

走的是一条公开 API 的路，没有 OPPO 私有 SDK、没有厂商白名单：

| 要求 | 做法 |
|---|---|
| 有标题 | `setContentTitle(...)` |
| 常驻 | `setOngoing(true)` |
| 合法样式 | `NotificationCompat.ProgressStyle`（四段 + 三个里程碑点） |
| 主动申请提升 | `setRequestPromotedOngoing(true)` |
| 清单声明 | `POST_PROMOTED_NOTIFICATIONS`（普通权限，装上就有） |
| 胶囊短文案 | `setShortCriticalText("1.24 / 2.00 km")` |

反面约束同样要守：不能是分组摘要、不能 `setColorized`、不能用自定义
`RemoteViews`、通道重要性不能是 `IMPORTANCE_MIN` —— 踩中任一条就退回普通通知。

`compileSdk` 因此提到 **36**（这套 API 到 Android 16 才有）；`targetSdk` 仍是 34。

设置页的「流体云」分段会把三种失败原因分开讲：系统太老（< API 36）、
没给通知权限、系统里「实时通知」被关掉。另有一条「发一条测试胶囊」，
8 秒后自动消失，不用真跑一轮就能看效果。

### 连不上服务器时

点【连接并拉取场地】如果拉不到数据，会弹一个明确的对话框（而不是默默留一个空列表）：

```
无法连接到服务器

连不上 sport.cqupt.edu.cn，场地列表没拉下来。

请检查：
· 手机是否连着网（校园网可能需要先登录）
· 能否正常打开微信小程序「重邮智慧体育」
· 稍等片刻再点一次「连接并拉取场地」
```

实现上把「网络层失败」和「业务层失败」分开了：`Api` 返回 `null` 是前者
（弹上面这个框），返回了 JSON 但 `code != 10200` 是后者（提示 openid 未绑定之类）。
原来的实现把两者都塞进一个 `lastError` 字符串，界面上根本分不出来。

## 主题

设置页里三选一：**跟随系统 / 深色 / 浅色**。选择会记住。

实现方式是 AppCompat 的 `DayNight`：

| 资源 | 浅色 | 深色 |
|---|---|---|
| `values/colors.xml` | `#F2F5FA` 底 / `#16202F` 字 | — |
| `values-night/colors.xml` | — | `#0B1220` 底 / `#E8EEF7` 字 |

所有颜色（背景、卡片、描边、强调色、成功/危险色，连按钮上的文字色）都走资源引用，
没有一处写死。切主题时 `AppCompatDelegate` 会重建界面 —— 而跑步线程归单例所有，
所以**切主题不会影响正在进行的打卡**。

### 主题为什么要放在 Application

`AppCompatDelegate.setDefaultNightMode()` 写在 `Activity.onCreate()` 里会**先白闪一下**：

```
Activity.onCreate()
  ├─ super.onCreate()          ← 此时按「跟随系统」解析主题
  │                              系统是浅色就用浅色，窗口已经画出来了
  ├─ setDefaultNightMode(深色)  ← 才发现该用深色 → 触发 Activity 重建
  └─ setContentView()           ← 重建之后才是深色
```

这也解释了为什么**设成浅色就没这个问题** —— 浅色 + 系统浅色不需要改，不触发重建。

放到 `App.onCreate()` 里就没事了：Application 比任何 Activity 都早，
主题在 Activity 创建之前就定好，一次到位，不重建。

（`App` 类已注册在 manifest 的 `<application android:name=".App">`。）

## 图标

用的是插画版——主角在操场上跑。源图 1024×1024。

**踩过的坑**：自适应图标的画布是 108×108，但系统**只渲染中间 72×72 那一块**并套蒙版。
我第一版预览时拿整块画布当圆，看起来"有个方框"，其实是预览比真实情况多露了一圈。
第二版又把插画裁到人物特写，构图丢了。

现在的做法：**整张插画缩到 70/108 居中**，图片方块的边落在可见区之外，
所以 bleed 永远看不见，也不会出现接缝；同时整张图完整可见。

## 版本记录

> **版本号规则变更**：从这一版起，版本号**只在明确要发版时才进位**。
> 日常提交、修 bug、调样式都不动版本号 —— 全部写进 `CHANGELOG.md` 的 `[Unreleased]`。
> 发版跑 `python release.py <major|minor|patch>`，它会改 `version.properties`、
> 把 `[Unreleased]` 改名成正式版本、打出 APK。详见 [`AGENT.md` §5.1](../AGENT.md#51-版本号规则semver)。

## 后台保活（v1.6 重点）

**症状**：息屏 / 退出 App 几分钟后，进度条几乎不动，只有「用时」在涨。

**根因**——节拍循环是按"睡了几次"算时间的：

```kotlin
var slept = 0L
while (slept < 8000) {
    Thread.sleep(250)
    slept += 250      // ← 假设每次都正好睡 250ms
}
```

息屏后 CPU 被挂起，`Thread.sleep(250)` 实际可能睡 2 秒，但代码还傻乎乎地
`slept += 250`。所以"8 秒"的一批实际拖了 12 秒以上，**整轮被拖长一倍多**。

**三处修复**：

| 修复 | 做法 |
|---|---|
| 1. 按真实时间计节拍 | 改用 `SystemClock.elapsedRealtime()` 定目标时刻，睡过头就立刻跳过剩余等待 |
| 2. CPU 唤醒锁 | `RunService` 里持一把 `PARTIAL_WAKE_LOCK`，息屏后 CPU 不睡 |
| 3. 电池优化白名单 | 界面里有状态条，未加入时会引导跳系统设置。**深度 Doze 会连唤醒锁一起忽略，只有进白名单才彻底** |

第 3 点是关键：Android 的 Doze 模式下，系统会**忽略 wake lock、挂起网络**，
前台服务只能保证进程不被回收，保不住 CPU。所以第一次用的时候，
点一下那条黄色的提示，把 App 加进白名单（只需设置一次）。

另外日志现在每 10 批打一行，能看出它确实在动：

```
批次 10/99　已跑 0.20/2.00 km　用时 01:20
批次 20/99　已跑 0.40/2.00 km　用时 02:41
```

### 关于「实时模式」

服务端的配速 = **「点开始到点结束的真实耗时」÷ 距离**。所以上传必须按真实节奏走，

挨个摄像头刷脸。

**这段时间你可以随便退出 App**：有前台服务守着，进程不会被系统回收。

## 常见问题

**Q：为什么不需要定位权限？**
A：因为根本不读 GPS。轨迹是本地算出来的，直接 POST 出去。

**Q：日志里 `isBind=false` 怎么办？**
A：openid 不对。重新抓一次，注意别把 `openid=` 后面的 `&` 一起复制进去。

**Q：token 过期了怎么办？**
A：不用管。每次点【开始打卡】都会重新换取 token。

**Q：能改跑步区域吗？**
A：区域是服务器下发的，App 只负责从里面挑一个生成闭环。
跑一次【连接】就能看到你这学期有几个可用区域。

**Q：中间断了怎么办？**
A：重来。但注意别在跑步过程中手动停止 —— 小程序那边手动停止会导致这次作废。
